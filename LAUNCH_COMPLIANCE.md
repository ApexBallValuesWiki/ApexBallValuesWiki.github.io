## Urgent: current shared worker

On October 30, 2026, an unauthenticated request to the *deployed* `GET /bug-reports` returned HTTP 200. Only the status/headers were checked; existing report content was **not** retrieved. The prior worker source returns stored report records, which may contain names, contact information, URLs or free text. The live `/roles` and `/fanart` endpoints also returned HTTP 200; their response bodies were not inspected. Treat the report inbox as potentially exposed until the worker is secured. Avoid submitting personal information in the meantime.

The changes in this archive are **local files only**. They do not fix the running worker or either hosted site until the owner coordinates and deploys them. Because this worker is shared, both staging and production are affected. Preserve evidence and have an authorized person privately assess the incident, logs, relevant notification obligations and whether unauthorized access occurred. Review legacy KV records, caches, backups and free-text fields under a documented retention/deletion plan; do not publish or copy sensitive records into tickets or public channels.

## Coordinated rollout — worker and both frontends

1. Back up the current worker and the shared KV data securely; record the deployment versions and rollback plan. Limit access to these backups. Do not delete or overwrite unrelated wiki, values, materials or deletion-registry data.
2. Rotate **every** team credential using secure, unique secrets. The old source used the publicly known default `apex2026`. This worker no longer creates or accepts that default, including for `/login`, writes, private reads or password changes. If any team member still has it, an authorized Cloudflare operator must provision a new unique password **out of band in the existing `adminPasswords` KV map**, preserving the other accounts; the ordinary change-password form intentionally cannot authenticate the known default. Never put real credentials in a repository, chat, screenshots or public logs. New account provisioning is also manual. New passwords through the form require at least 12 characters; longer unique passphrases are recommended.
3. Deploy `scripts/cloudflare-proxy-worker.js` to the *shared* worker only after coordinating the change with both teams. Its `/version` should then report `2026-10-30.2`. The new worker requires credentials to read bug reports and the team role map; it accepts only the new fixed-choice `structured-v1` public reports and reconstructs their fields server-side. It excludes pending fan art from public reads and strips selected staff metadata recursively from public data. This is not a complete audit of personal information inside arbitrary text or images.
4. Update **both** frontend deployments promptly. The new frontend sends fixed choices without free text/contact and sends credentials to staff report and fan-art tools. Until a cached/old frontend is updated, old report submissions will be rejected and old staff inbox/pending-art views may stop working. This temporary incompatibility is preferable to retaining the public inbox. The service-worker cache/release identifiers have been bumped, but confirm installed clients update; stale clients and old assets can persist.
5. Verify without fetching real reports: unauthenticated `GET /bug-reports` and `/roles` return 401; public fan-art responses contain only approved material; a test account with a rotated credential can access staff tools; fixed-choice test reports contain no free text/contact; normal public unit data and both sites still work. Check the worker's production logs and rate limits. Keep this checklist and the release records private where appropriate.
6. The shared KV full-bundle version check is best effort, not an atomic compare-and-swap: simultaneous writes can still race. Use a transactional coordinator such as a Durable Object before relying on concurrent publishing for data integrity. The updated worker also rejects ordinary full-bundle writes without a version and preserves omitted sections; very old admin clients may need an update.
7. Audit/history writes are best effort and are **not transactional** with the database write. The updated worker archives evicted recent-feed and per-unit records before trimming, and reports an audit failure if storage fails, but concurrent KV operations can still race. History already deleted by older versions cannot be recovered by this update. Review archive retention and access controls, back up `auditArchive:` keys with the rest of KV, and use a transactional audit store for dependable compliance records.
8. Replace the current password-in-localStorage/password-map architecture with a reviewed identity solution, MFA, short-lived sessions, strong secret handling and distributed rate limiting. The worker's current in-memory rate limiting is per isolate and cannot guarantee abuse prevention. Restrict privileged endpoints at the edge where possible. The frontend/source history already contains team addresses; restricting `/roles` does not make those addresses secret. Removing metadata keys does not remove an email written inside a description, image, announcement, fan-art artist name, or other free-text content. Audit those separately.
9. Review the existing deployment helpers before using them: the Linux/macOS `push.sh` and `push-test.sh` use `git push --force`, which can overwrite remote history. Prefer a reviewed non-force push and do not run any helper until the shared-worker rollout and backups are coordinated.

### Staging confidentiality

The staging `AccessGate` now checks saved credentials with the worker and fails closed in the UI while checking. **It does not make GitHub Pages private.** Static HTML, scripts, source maps and other published files can still be fetched directly. To make staging genuinely team-only, move it to private hosting or put every asset and route behind server/edge access control (for example, a correctly configured Cloudflare Access-protected origin). Ensure the direct GitHub Pages URL cannot bypass that protection; test anonymous direct file access as well as the visible page. Keep ads disabled on staging.

## Before considering AdSense

Ads stay off even on the production host. The publisher ID and `public/ads.txt` are present for the specified production account, but account ownership, domain verification, ad slots, inventory and site approval must be verified in the actual AdSense account; none can be guaranteed from this repository. The account holder must meet Google's age requirements.

1. Complete and document the child-directed/mixed-audience assessment. Configure Google's current **Tag for age treatment (TFAT)** and other applicable child/teen protections before every eligible ad request; child treatment (`1`) disables personalized ads and remarketing and restricts third-party ad vendors, but **does not** replace parental consent or legal review. This code includes a future `data-tag-for-age-treatment="1"` on its disabled slot only; validate current Google requirements and all request paths before using it.
2. Choose and integrate an appropriate consent-management platform. Google says publishers serving personalized ads in the EEA, UK or Switzerland must use a Google-certified CMP integrated with the IAB TCF. Certified does not mean legally compliant, and child-privacy, non-personalized/limited ads, geographic applicability and regional opt-outs require separate review. The local statistics banner is **not** a Google-certified CMP and grants no advertising consent.
3. Implement the chosen CMP's region-appropriate messages, consent defaults, signaling, persistent/reopenable settings and withdrawal/opt-out mechanisms. If using Google's European regulations message, provide its prescribed revocation link. Consider applicable US state privacy/GPP and “Do Not Sell or Share” choices. Do not load advertising or consent-required third-party scripts on policy pages or before a valid applicable decision. Test first visits, rejection, withdrawal, children, all relevant regions, blocked storage and refreshes with browser network inspection.
4. Finish and publish accurate privacy/advertising disclosures: technologies, data use, ad partners, personalization, choices and Google/partner links as applicable. Account for the actual CMP, vendors and purposes rather than leaving generic placeholder text.
5. Check Google Publisher Policies, placement, content quality, page speed, mobile behavior, unauthorized/incentivized clicks, `ads.txt`, site ownership, `ca-pub-2832011907708910`, and approval in AdSense. Do not show ads on admin, privacy, terms, gates, error, empty or other ineligible screens. Limit placement only to reviewed content pages and label it clearly.
6. Only after legal, security, Google account, CMP and child-protection requirements have been signed off and independently tested, implement the appropriate ad-consent state machine and consider a controlled production launch. `ADS_LAUNCH_READY` alone is not a CMP, geo/age decision, parental-consent mechanism or approval.
